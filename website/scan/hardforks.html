Planned hard forks

Not on the chain yet. A planned fork has no date: it switches on at a block height only after every witness runs a release that knows it and the witnesses vote it in.

  • HF-9 — One keyed tree for the chain’s growing state. Coins first, then tokens, names and claims, together with the storage registry and the storage segment list, move into one keyed tree that is updated block by block; storage segment assignment moves to rendezvous hashing. A light client or a light storage node could then prove a single record without downloading whole lists. Not voted: the byte layout and the block height are not decided.
  • Native DEX order rule (no number yet). Limit orders on Nodus itself, not through the EVM, need a hard fork. Planned and not designed yet; it starts on the testnet with test tokens.
