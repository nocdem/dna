# IXIOS post-handoff candidate

This is new work after the immutable 2026-11-02 09:43 extension / 09:46 source handoff. IXIOS is not XION. Do not describe the delivered seven-network package as containing IXIOS sends.

## Current scope

Native ML-DSA-87 transfers between empty-code accounts on the Ixios main network and the Ixios test network, with an explicit gas-price cap, fixed native 1,000 gas and local signing. Both are selectable in the network selector (`web-wallet/extension/src/constants/networks.js`); the extension offers send and history on both (`extension/src/constants/capabilities.js`). The web wallet and Connect show the same choice and read the balance, but send stays off with the note "Send IXIOS from the extension." Trusted extension only; no website-provider permissions. The trusted extension mainnet code-candidate gate is enabled after bounded independent review and native admission evidence, including externally supplied browser-WASM signed bytes executed by the pinned node without re-signing (10/10 native cases). Other networks and website-provider sends remain disabled. Runtime must fail closed if fresh network/fee/account checks fail; this is not a claim of verified usable live access. No live signed transaction or financial broadcast has been performed.

The two networks are the two entries of `IXIOS_NETWORKS` in `web-wallet/src/pq/ixios/network.js`. Nothing is detected from a node answer; each network's values are fixed there, and each entry is identified by its genesis hash (block 1's parent hash), never by chain id alone.

Signing: the chain id is part of the signing hash (`src/pq/ixios/transaction.js` `ixiosSigningHash`), and `v` is `2 * chainId + 35`: 0x25 on the main network and 0x29 on the test network. The chain-3 bytes (hash and serialization) are checked against the pinned reference vector `web-wallet/test/ixios-reference/vectors-chain3.json`, generated by the Go oracle in the same directory; `test/ixios-transaction.test.js` replays it with `{networkId:'testnet'}`. This is codec evidence only, not transaction admission.

Empty-code check: the main network uses `getCode`. The test node has no `getCode`, so the test network uses `getProof`; the account has no code exactly when the answer's `codeHash` is the zero hash or the hash of empty code (`ixiosProofCodeEmpty`). Like `getCode`, the answer is the provider's; the `accountProof` in it is not checked against a state root.

Observed on the test node (per the comment in `network.js`): the `ixios_` method names (no `eth_` name exists there), chain id 3, the genesis hash, and no `getCode`. Not observed: Aegis height 300 is the reference's value for chain id 3; the height the running node uses is not established. Acceptance of an ML-DSA-87 transaction by the v1.3.0-dev test node is not yet observed; the operator's first real send is still to come (plan section 9.7). The native admission evidence above was obtained for the main network only.

Browser reads: from the sites (`wallet.nodusnetwork.io`, `connect.nodusnetwork.io`) a browser read of either node failed with "Failed to fetch" in the probe of 2026-11-12, and the response headers captured with it show the CORS header `access-control-allow-origin: *` sent twice, which a browser rejects (`docs/research-evidence/2026-11-12-ixios-testnet-rpc/cors-probe-result.txt`; the file does not say which node sent the doubled header). The extension is the only surface that sends.

The account has a 48-byte address. Chain ID 1 alone is insufficient network identification because it collides with Ethereum; for each network, block 1's parent hash must equal that entry's genesis hash (table below). Native block timestamps are milliseconds, not Ethereum-style seconds.
